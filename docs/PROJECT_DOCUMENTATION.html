1. Project Overview

The Job Market Intelligence Agent is an advanced AI-powered system that analyzes the technology job market. Instead of a simple chatbot, this is a Multi-Agent System where multiple specialized AI agents work together to:

  • Search real job postings from multiple job boards (Adzuna, Arbeitnow)
  • Extract and rank the most in-demand tech skills
  • Parse salary ranges from job descriptions
  • Analyze GitHub activity for technology trends
  • Compare job markets across different countries
  • Upload your resume and find skill gaps compared to market demands
  • Generate comprehensive, evidence-based market reports
  • Hold a real conversation — greetings, off-topic questions, and natural follow-ups ("what about India?") are handled without re-running the whole pipeline
Key Principle: This system guarantees zero hallucination. Every statistic in every report comes from real-time job posting data fetched via tools — never from the LLM's memory.
What's new in v1.1: A deterministic query classifier now sits in front of the pipeline. Conversational or off-topic messages ("hi", "what's the weather?") get a direct answer from the ChatResponder agent and never trigger the full analytical pipeline — fixing the earlier behavior where every message produced the same market report regardless of what was asked.

2. Why This Project Exists

The Problem

Job seekers and career advisors struggle to get accurate, real-time data about the technology job market. Generic AI chatbots give outdated or hallucinated statistics.

The Solution

A multi-agent AI system that fetches real job postings, extracts skills/salaries via deterministic tools, and produces evidence-based reports with traceable data sources.

3.2 Request Flow Example

When a user types "What are the top Python skills in Germany?":

  1. Chainlit UI receives the message, creates initial GraphState
  2. Query Classifier deterministically tags the intent as analytical → routes to the Planner (a purely conversational message would route to ChatResponder and stop here)
  3. Planner Agent extracts role="Python Developer", country="Germany", creates execution plan
  4. Market Collection Agent calls Adzuna API + Arbeitnow API to fetch real job postings
  5. Skill Extraction Agent scans job descriptions, counts skill frequencies, computes statistics
  6. Recommendation Agent turns the statistics into prioritized advice
  7. Final Answer Agent writes a concise, question-aligned answer (no LLM — always runs even if Groq is down)
  8. Report Generation Agent compiles everything into a structured markdown report and saves it to reports/ via the Filesystem MCP
  9. Chainlit UI streams the direct answer first, then the full report, back to the user in real-time
Multi-turn example: If the user follows up with just "what about salaries?", the classifier and planner reuse the role and country from conversation_history — no need to repeat "Python Developer in Germany".

7. Multi-Agent System (LangGraph)

7.1 What is LangGraph?

LangGraph is a library for building state machines using LLM agents. Think of it as a flowchart where:

  • Each node is an agent (a function that processes state)
  • Each edge is a transition (conditional or fixed)
  • The state is a shared dictionary that flows between nodes

7.2 The Eleven Agents

1. Query Classifier Front Door

File: agents/classifier.py

Job: Deterministically decides whether the message is analytical or conversational, before anything expensive runs.

  • No LLM call — fast, predictable, works even with zero API keys configured
  • Detects intent: job_market, tech_trend, salary, comparison, resume_analysis, general_chat, out_of_scope
  • Analytical intents route to the Planner; everything else routes to ChatResponder

Why: Without this, every message — including "hi" or a weather question — triggered the full market-analysis pipeline and produced the same report regardless of what was asked. The classifier fixed that.

2. Chat Responder Direct Answer

File: agents/chat_responder.py

Job: Answers conversational and off-topic queries directly, without the analytical pipeline.

  • Handles greetings, thank-yous, "what can you do", and genuine off-topic questions
  • Optionally grounds itself with the Search MCP's web_search tool and cites sources
  • Ends the graph immediately — no report is generated

Why: Keeps the system honest about what it's for, and avoids wasting LLM/API calls on questions the market-analysis pipeline can't actually answer.

3. Planner Agent Orchestrator

File: agents/planner.py

Job: Understands the user query and creates an execution plan.

  • Extracts the target role (e.g., "Data Scientist", "Python Developer") using keyword matching
  • Extracts the target country (e.g., "Germany", "US") using keyword matching
  • Calls the LLM to produce a structured JSON execution plan
  • Validates the plan using Pydantic PlannerOutput
  • Falls back to a default plan if LLM fails

Why: Without a planner, every query would trigger every agent, wasting time and API calls. The planner routes only necessary agents.

4. Market Collection Agent Data Fetcher

File: agents/market_collection.py

Job: Fetches real job postings from external APIs.

  • Calls search_jobs() tool which hits Adzuna + Arbeitnow APIs (also exposed as the Jobs MCP)
  • Splits the maximum results between sources (e.g., 50/50)
  • For multi-country queries, issues one call per country in state["countries"] and merges results, splitting the result budget across markets
  • Returns serialized JobSearchResult to state

Why: This is where real data enters the system. All subsequent analysis depends on this agent's output.

5. Skill Extraction Agent Analyzer

File: agents/skill_extraction.py

Job: Processes raw job postings to extract structured skill and salary data.

  • Deserializes job results from state
  • Enriches each posting with extracted skills (via regex patterns)
  • Computes skill statistics (frequency counts across all postings)
  • Parses salary ranges from job descriptions
  • Returns top 50 skills and salary data

Why: Raw job descriptions are unstructured text. This agent turns them into quantifiable data.

6. Trend Analysis Agent Trend Tracker

File: agents/trend_analysis.py

Job: Measures technology popularity using GitHub activity + job market data.

  • Only runs when specific technologies are mentioned in the query
  • Fetches GitHub stats (stars, forks, contributors) via analyze_github_trends tool
  • Combines GitHub data with job skill counts
  • Computes a popularity score (0-100) using a weighted formula

Why: Job demand alone doesn't show the full picture. GitHub activity indicates developer adoption and community health.

7. Resume Analysis Agent Gap Finder

File: agents/resume_analysis.py

Job: Compares a user's resume against current market demands.

  • Runs only if a resume was uploaded and this turn's intent is actually resume-relevant — a resume from earlier in the chat no longer forces a stale gap report onto an unrelated question
  • Reads the file via the Filesystem MCP's read_file tool
  • Parses uploaded resume (PDF, DOCX, or TXT)
  • Extracts skills mentioned in the resume
  • Compares against top 30 market skills from Skill Extraction
  • Computes: matching skills, missing skills, bonus skills (in resume but not in market)
  • Calculates a gap_score (0 = perfect match, 100 = major gaps)

Why: Helps job seekers understand exactly which skills they need to learn to be competitive.

8. Comparison Agent Multi-Country

File: agents/country_comparison.py

Job: Produces a dedicated side-by-side comparison when the query asks about more than one country.

  • Runs only when the plan contains a compare_countries task
  • Re-checked after both the trend-analysis and resume-analysis branches, so a comparison query is never silently skipped just because no resume was uploaded
  • Calls the Jobs MCP's compare_countries tool
  • Produces posting volume, salary ranges, and shared vs. country-unique skills per market

Why: A single-country pipeline can't naturally answer "US vs UK" — this agent is a dedicated step so comparison queries get first-class treatment instead of being bolted onto the market-collection agent.

9. Recommendation Agent Advisor

File: agents/recommendation.py

Job: Generates actionable recommendations based on all analysis results.

  • Builds a summary of all analysis data
  • Calls the LLM with a specialized recommendation prompt
  • Skips any skill the user already has, so recommendations only show genuine gaps
  • Falls back to rule-based recommendations if LLM call fails

Why: Raw data needs interpretation. This agent turns statistics into actionable career advice.

10. Final Answer Agent Concise Answer

File: agents/final_answer.py

Job: Writes the short, question-aligned answer the user actually sees first in chat.

  • Rule-based — no LLM call, so it always runs even if Groq is unavailable
  • Reads the full state and composes a heading plus a few bullet points that answer exactly what was asked
  • Checks intent as well as data presence, so an unrelated follow-up doesn't get a stale resume/comparison answer

Why: The full report is thorough but long. Most users want the answer, not a wall of tables — this agent gives them that first, with the full report still available underneath.

11. Report Generation Agent Compiler

File: agents/report_generation.py

Job: Compiles all results into a final, structured market report.

  • Uses ReportBuilder (fluent builder pattern) to add sections
  • Adds skill statistics, salary data, trends, resume analysis, recommendations
  • Generates executive summary via LLM
  • Always includes data limitations disclaimer
  • Produces a MarketReport with to_markdown() method, and saves it to reports/ on disk via the Filesystem MCP's save_report tool

Why: Provides a consistent, well-formatted output regardless of which agents ran, and keeps a durable record separate from the concise in-chat answer.

8. MCP (Model Context Protocol) Servers

8.1 What is MCP?

MCP is like USB-C for AI. It defines a standard way for AI agents to discover and use tools, regardless of what the tools do internally.

Analogy: Before USB, every device had a different port. Before MCP, every AI tool had a different calling convention. MCP standardizes tool interfaces so agents don't need to know the implementation details.

8.2 Our Five MCP Servers

1. GitHub MCP Server github_mcp.py

Provides 3 tools for GitHub data:

  • get_repo_stats — Fetches stars, forks, issues, contributors for a repository
  • search_repositories — Searches GitHub repos by topic/keyword
  • get_trending — Gets trending repositories

2. Filesystem MCP Server filesystem_mcp.py

Provides 3 tools for file operations:

  • read_file — Reads file contents (with path traversal prevention)
  • list_directory — Lists directory contents
  • save_report — Saves generated reports to disk

Security: Only allows access to ALLOWED_DIRECTORIES — prevents reading system files.

3. Search MCP Server search_mcp.py

Provides 3 tools for web search:

  • web_search — General web search via Tavily
  • search_tech_news — Searches for technology news specifically
  • search_market_reports — Searches for market analysis reports

4. Reddit MCP Server reddit_mcp.py Optional

Provides 2 tools for Reddit community data:

  • search_posts — Searches tech subreddits (r/programming, r/python, r/javascript, etc.)
  • get_tech_sentiment — Analyzes community sentiment about technologies

Note: Gracefully handles missing Reddit credentials — the system works without it. Currently registered but not hardwired to any agent — available for the LLM Planner to opt into via a task's required_mcp_servers.

5. Jobs MCP Server jobs_mcp.py NEW

9. Tools — The Anti-Hallucination Layer

The Hallucination Problem: If you ask an LLM "What percentage of jobs require Python?", it will confidently give you a number — but it's made up. The LLM has no access to real job postings. This system solves that by having the LLM call tools that fetch real data.

9.1 How Tool Calling Works

  1. LLM receives a prompt and decides it needs data
  2. LLM emits a tool call (e.g., search_jobs(query="Python", country="Germany"))
  3. The system executes the tool — which calls real APIs, runs regex extraction, etc.
  4. Tool results are returned to the LLM
  5. LLM interprets the results and generates a response based on real data

9.3 The Popularity Score Formula

popularity_score = (log_scaled_github_stars × 0.5) + (job_demand_percentage × 0.5)

Where:
  log_scaled_github_stars = (log(stars + 1) / log(max_stars + 1)) × 50
  job_demand_percentage   = (tech_job_count / total_job_count) × 50
  Maximum possible score  = 100

14.2 Report & Recommendation Prompts (prompts/report_prompt.py)

  • REPORT_SYSTEM_PROMPT — rules for writing evidence-based reports:
    • Every statistic must cite its source
    • Never use "approximately" for data you don't have
    • Always include data limitations section
  • RECOMMENDATION_SYSTEM_PROMPT — rules for generating prioritized recommendations:
    • Base recommendations on actual skill statistics
    • Prioritize by market demand percentage
    • Include both quick wins and long-term goals
Why separate prompts? Each agent has a distinct role and needs different instructions. Keeping prompts in dedicated files makes them easy to iterate on without touching agent logic.

20. FAQ & Troubleshooting

Common Issues

Q: "ModuleNotFoundError: No module named 'api'"

Cause: You're running from the wrong directory.

Fix: Always run from the project root (L2_Project/). The api, agents, etc. are top-level packages.

Q: " connection refused" on PostgreSQL

Cause: Docker container not running.

Fix: docker compose up -d postgres and wait ~5 seconds for it to initialize.

Q: "GROQ_API_KEY not set" warning

Cause: .env file missing or not in project root.

Fix: Copy .env.example to .env and fill in your keys.

Q: Chainlit shows "Error connecting to LLM"

Cause: Invalid Groq API key.

Fix: Verify your key at console.groq.com. Ensure no extra spaces in .env.

Q: "alembic" command not found

Cause: Alembic not installed or venv not activated.

Fix: pip install alembic and activate your virtual environment.

Q: Skills not found in job postings

Cause: Too few job postings returned (need minimum data for statistics).

Fix: Try broader queries (e.g., "Python developer" instead of "Senior ML Engineer specializing in PyTorch at startup").

Q: I set DATABASE_URL in .env but the app still connects to the default database

Cause: config.py's field is named SQLALCHEMY_DATABASE_URL, not DATABASE_URL. Because extra="ignore" is set, a wrongly-named variable is silently dropped instead of erroring.

Fix: Use SQLALCHEMY_DATABASE_URL=... in your .env (see the corrected .env.example).

Q: Why does GET /api/query/{id} return 404 instead of an error for a bad id?

Cause: Query and resume ids are UUIDs. Passing a malformed string used to raise an unhandled database error, which the global exception handler turned into a confusing 500.

Fix: Already handled — database/repositories.py validates the id with uuid.UUID(...) before querying and returns a clean "not found" for anything malformed.

Q: How do I add a new skill to detect?

File: tools/skill_extractor_tool.py

Add a new regex pattern to the SKILL_PATTERNS dictionary and add an alias to services/normalization_service.py SKILL_ALIASES.

Q: How do I add a new MCP server?

  1. Create mcp_servers/your_server.py extending MCPServer
  2. Implement name, get_tools(), call_tool()
  3. Register it in mcp_servers/registry.py
